# Secrets Management Guide

Every credential lives in AWS Secrets Manager, provisioned by `SecurityStack`
(`infrastructure/src/main/java/com/wealthynest/infrastructure/stacks/SecurityStack.java`). Nothing
is ever hardcoded in CDK, in a workflow file, or in a script — `deploy-backend.sh` reads all of
this fresh from Secrets Manager/SSM Parameter Store on every deploy and writes it to
`/opt/wealthynest/current.env` (mode `600`, owned by the `wealthynest` user, never committed
anywhere, never logged).

## The 8 secrets

| Secret name | Maps to env var(s) | Source |
|---|---|---|
| `wealthynest-production-db-credentials` | `DB_USERNAME`, `DB_PASSWORD` | **Auto-generated by CDK.** Never needs manual action. |
| `wealthynest-production-jwt-secret` | `JWT_SECRET` | **Auto-generated by CDK.** Never needs manual action. |
| `wealthynest-production-google-oauth-client-secret` | `GOOGLE_NATIVE_CLIENT_SECRET` | **Manual.** From the "Desktop app" OAuth client in Google Cloud Console (see `wealthynest-api/.env.example`). |
| `wealthynest-production-smtp-credentials` | `MAIL_USERNAME`, `MAIL_PASSWORD` | **Manual.** Brevo SMTP login + API key. |
| `wealthynest-production-vault-encryption-key` | `VAULT_ENCRYPTION_KEY` | **Manual, `openssl rand -base64 32` exactly.** Rotating this makes every existing Vault item unreadable — generate once, keep it. |
| `wealthynest-production-vault-hash-pepper` | `VAULT_HASH_PEPPER` | **Manual, `openssl rand -base64 32` exactly.** Deliberately separate from the encryption key above. |
| `wealthynest-production-fcm-service-account` | `FCM_SERVICE_ACCOUNT_JSON` | **Manual, optional.** Base64-encoded Firebase service-account JSON — see `ANDROID_APP_ROADMAP.md`. Left as the placeholder, push notifications silently no-op. |

Beyond the 4 literally named in the original brief (DB, JWT, Google OAuth, SMTP), the Vault keys
and FCM credential were added because `wealthynest-api`'s own `application.yml` requires them at
boot just as much — leaving any of them hardcoded or undocumented would have failed "never
hardcode secrets" exactly as much as skipping the JWT secret would.

### Populating a placeholder secret

```bash
aws secretsmanager put-secret-value \
  --secret-id wealthynest-production-google-oauth-client-secret \
  --secret-string 'the-real-value'

# JSON-shaped ones (smtp-credentials):
aws secretsmanager put-secret-value \
  --secret-id wealthynest-production-smtp-credentials \
  --secret-string '{"MAIL_USERNAME":"xxx@smtp-brevo.com","MAIL_PASSWORD":"xsmtpsib-..."}'
```

No redeploy is needed to pick up a new secret value — the *next* deploy (or a manual
`deploy-backend.sh <bucket> <key> <version>` re-run) reads it fresh. To apply it immediately
without a full deploy, SSM into the instance and `sudo systemctl restart wealthynest-backend`
after confirming `current.env` would be rewritten (or just trigger a no-op backend deploy).

## Non-secret runtime config (SSM Parameter Store, not Secrets Manager)

A hostname isn't sensitive — mixing it into Secrets Manager would just be noise there. These are
plain `AWS::SSM::Parameter` values, written by `DatabaseStack`/`ComputeStack`, read the same way:

| Parameter | Maps to | Source |
|---|---|---|
| `/wealthynest/production/db-url` | `DB_URL` | RDS endpoint, computed by CDK |
| `/wealthynest/production/redis-host` | `REDIS_HOST` | ElastiCache endpoint, computed by CDK |
| `/wealthynest/production/redis-port` | `REDIS_PORT` | ElastiCache port, computed by CDK |
| `/wealthynest/production/rate-limit-trusted-proxies` | `RATE_LIMIT_TRUSTED_PROXIES` | Same Cloudflare IPv4 range list as `cdk.json`'s `cloudflareIpv4Ranges` — single-sourced, not hand-copied |
| `/wealthynest/production/cloudwatch-agent-config` | (not app config) | CloudWatch Agent's own metrics/log config |

`GOOGLE_CLIENT_ID` and `GOOGLE_NATIVE_CLIENT_ID` are public OAuth client IDs, not secrets and not
CDK-managed — set them directly in `deploy-backend.sh`'s `write_env_file` (two blank lines with a
comment) once you've created the OAuth clients. Left blank, the Google sign-in button just doesn't
render — a safe default, unlike a blank JWT secret would be.

## IAM access to secrets — who can read what

- The **EC2 instance role** (`ComputeStack`) can read exactly these 7 secrets and 4 parameters,
  granted individually via CDK's `secret.grantRead(role)` / `parameter.grantRead(role)` — check
  the role's inline policy in the AWS Console if you ever need to confirm scope; there is no
  wildcard `Resource: "*"` anywhere in it.
- **GitHub Actions' `BackendDeployRole`** (`CicdStack`) cannot read any of these secrets at all —
  it only uploads a JAR to S3 and triggers `deploy-backend.sh` over SSM; the instance reads its
  *own* secrets with its *own* role, so the secret values never pass through a GitHub Actions
  runner or log.
- **Nobody else** — no other IAM principal in this stack set is granted read access to any of
  these 7 secrets.

## Rotation

- `db-credentials`, `jwt-secret`: safe to rotate any time — generate a new `SecretStringGenerator`
  value (or use Secrets Manager's built-in rotation if you wire up a rotation Lambda later) and
  redeploy; the app reads it fresh on every deploy/restart.
- `vault-encryption-key`, `vault-hash-pepper`: **do not rotate casually** — see the secret's own
  description. Only rotate as part of a deliberate, planned Vault data migration.
- `google-oauth-client-secret`, `smtp-credentials`, `fcm-service-account`: rotate whenever the
  upstream provider (Google/Brevo/Firebase) issues a new one — `put-secret-value` + redeploy.
